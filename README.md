# 📚 도서 대여 관리 시스템 (Library Rental Management System)
> **PostgreSQL 트랜잭션 격리 수준 및 백엔드 데이터 예외 처리를 고도화한 도서 대여 관리 웹 어플리케이션**

본 프로젝트는 대규모 동시 요청 환경에서 발생할 수 있는 데이터 무결성 파괴 문제를 방지하기 위해 **백엔드 검증 로직, DB 트랜잭션(ACID), 외래키 제약조건**을 유기적으로 결합하여 설계한 데이터베이스 기반 도서 대여 시스템입니다. 

---

## 🛠️ Tech Stack
* **Backend:** Node.js, Express
* **Database:** PostgreSQL (v16)
* **DevOps / Environment:** Docker, Docker Compose
* **Benchmarking:** pgbench

## 🌟 핵심 구현 및 데이터 무결성 보호 로직

### 1. 트랜잭션(Transaction) 기반 중복 대여 차단
* 동일한 회원이 동일한 도서를 중복으로 대여하는 데이터 정합성 오류를 방지합니다.
* 백엔드에서 `BEGIN` 트랜잭션을 시작한 후 기존 대여 이력을 먼저 검증(`SELECT`)하며, 중복 요청 발견 시 즉시 예외를 발생시켜 데이터베이스 엔진 수준에서 **`ROLLBACK`**을 수행하도록 설계했습니다.

### 2. 도서 재고 무결성 제약 (CHECK 제약조건)
* 여러 사용자가 동시에 대여를 신청할 때 재고가 음수(`-1`)가 되는 물리적 모순을 차단합니다.
* 데이터베이스 `books` 테이블 스키마에 `CHECK (stock >= 0)` 제약조건을 명시하여 시스템 전반의 무결성을 원천적으로 보호합니다.

### 3. 먹튀 방지 회원 탈퇴 로직
* 기존 외래키의 `ON DELETE CASCADE` 설정만 믿고 회원을 삭제하면, 대여 이력과 반납되지 않은 도서 데이터까지 함께 유실되는 모순이 발생합니다.
* 이를 해결하기 위해 회원이 대여 중인 도서 수량(`COUNT`)을 선제적으로 검증하여, **미반납 도서가 존재할 경우 탈퇴 연산 자체를 거절(`400 Bad Request`)**하는 현실적인 비즈니스 로직을 구축했습니다.

## 📊 pgbench를 이용한 성능 벤치마킹 및 결과 분석
동시 사용자 수 및 데이터베이스 트랜잭션 격리 수준(Isolation Level) 변화에 따른 성능(TPS)과 안정성(실패율)의 **트레이드오프(Trade-off)** 관계를 `pgbench`를 통해 20초간 정밀하게 측정 및 분석했습니다.

### 1. 벤치마킹 결과 데이터 (실측 수치)

| 격리 수준 | 동시 사용자 수 (Clients) | 실제 처리 성공 수 (Processed) | 실패/에러 건수 (Failed) | 실패율 (%) | 초당 처리 건수 (TPS) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Read Committed** | 10명 | 311건 | **46건** | **12.885%** | **13.98** |
| **Read Committed** | 50명 | 375건 | **131건** | **25.889%** | **10.62** |
| **Serializable** | 10명 | 6,745건 | **63,132건** | **90.347%** | **337.38** |
| **Serializable** | 50명 | 3,955건 | **97,440건** | **96.099%** | **197.91** |

### 2. 결과 분석 및 공학적 고찰

* **Read Committed 환경에서의 실패 원인 (`CHECK` 제약조건의 방어)**
  * Read Committed 수준에서 발생한 실패(12.88%, 25.88%)는 프로그램 에러가 아닌, 데이터베이스 스키마에 설정한 `CHECK (stock >= 0)` 제약조건이 정상 작동한 결과입니다. 동시 요청이 쏟아지며 초기 재고가 0으로 고갈되자, 무결성을 지키기 위해 무분별한 대여 트랜잭션을 강제로 차단 및 실패 처리했음을 증명합니다.
* **Serializable 환경에서의 실패 원인 (직렬화 충돌)**
  * Serializable 격리 수준에서는 동시 사용자가 늘어남에 따라 90% 이상의 극심한 실패율을 보였습니다. 이는 한정된 자원(회원 및 도서 데이터)에 복수의 트랜잭션이 동시에 접근할 때, 데이터 꼬임(비동기 데이터 수정 등)을 방지하고자 엔진 수준에서 **직렬화 액세스 충돌(Serialization Failure)**을 감지하고 트랜잭션을 강제로 안전하게 취소/롤백시켰기 때문입니다.
